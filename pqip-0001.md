# PQIP 1: PQIP purpose and process

## Abstract

A PostQuantum Cash Improvement Proposal (PQIP) is a public design document for a change to PQCH:
its consensus rules, its peer-to-peer protocol, its node and wallet behaviour, or the way the
project works. This PQIP says what a PQIP is, how it is written, how it is discussed, how it moves
from an idea to a final document, and how a consensus change is activated on the network.

## Motivation

PQCH has no company, foundation, issuer or treasury behind it, and nobody can decide for the
network. Its rules change only when the people who run nodes choose to run new software and, for
soft forks, when miners signal that they are ready. PQIPs give everyone the same place to propose
a change, the same written specification to review and to implement, and a permanent record of why
each rule is the way it is.

## What a PQIP is

| Type | What it covers | Example |
| --- | --- | --- |
| Consensus | Which blocks and transactions are valid. Needs a soft fork or a hard fork. | The ML-DSA emergency soft fork |
| Network | The peer-to-peer protocol and node policy (relay, mempool, anti-DoS). | How a header with a new Monero key is checked |
| Applications | Wallets, mining, address formats, derivation, interfaces between programs. | 24-word recovery and the post-quantum seed |
| Informational | Guidelines and background; nobody has to follow them. | Recommended confirmations for payments |
| Process | How the project works, including this document. | PQIP 1 |

A PQIP describes one idea. A change too small to need a design discussion (a bug fix, a clearer
error message) does not need a PQIP: a pull request is enough.

## Format

A PQIP is a Markdown file in the PQIP repository, named `pqip-NNNN.md`, with the header shown at the
top of this document and these sections:

1. **Abstract**: a short summary.
2. **Motivation**: the problem it solves and why the current rules are not enough.
3. **Specification**: precise enough for an independent implementation to behave the same way.
4. **Rationale**: the alternatives considered and why they were not chosen, and the objections raised
   in the discussion and how they were answered.
5. **Backwards compatibility**: what happens to nodes, wallets and miners that do not upgrade.
6. **Deployment**: for consensus PQIPs, the activation parameters (see below).
7. **Reference implementation and tests**: a link to the code and to the tests; required before Final.
8. **Security considerations**: what an attacker could do with the change, and what it costs them.

PQIPs are written in English. Every PQIP is dedicated to the public domain under CC0-1.0, so that
anyone may copy, translate, adapt and implement it without asking or crediting anyone. A
specification has to be free to reuse in other software, documentation and translations, and CC0
(with its fallback licence where a full waiver is not possible) is the simplest way to say so.

## Life cycle

```
Draft ──► Proposed ──► Final
  │           │
  └──► Withdrawn / Rejected
```

- **Draft.** Anyone may open a pull request with a new PQIP. The editors check only the form (header,
  sections, that it is one idea, that it is not a duplicate) and assign the next free number. A
  number says nothing about whether the idea is good.
- **Proposed.** The author asks for it when the specification is complete and a reference
  implementation exists. Discussion happens in public: the pull request, the PQCH forum and the
  Matrix room. The PQIP stays Proposed while open technical objections are being answered.
- **Final.** For a consensus PQIP: when the change is active on the main network. For the other
  types: when the implementation is merged and released, and no open objection remains that the
  rough consensus of the discussion considers unanswered. Small corrections are still allowed after
  Final; changes in behaviour need a new PQIP that replaces it.
- **Withdrawn**: the author gave it up. **Rejected**: it found no rough consensus, or it was replaced.
  A Proposed PQIP with no activity for one year may be marked Rejected by the editors; the author may
  ask to reopen it.

Nobody votes on PQIPs. Rough consensus means that objections were heard and answered, not that
everybody agrees. The editors record the outcome; they do not decide it.

## Consensus changes and activation

- **Soft forks** (rules that make fewer blocks or transactions valid) are activated by miner
  signalling in block versions (BIP9-style version bits). A deployment period is **1,440 blocks**
  (about one day); the new rules lock in when **at least 90% of the blocks of one period (1,296)**
  signal, and become active one period later. The PQIP states the bit, the start time, the timeout
  and any minimum activation height. If the timeout passes without lock-in, the deployment fails and
  needs a new PQIP or new parameters.
- **Hard forks** (rules that make more blocks or transactions valid) split the network if not every
  node upgrades. The project does not plan any. A hard fork PQIP must explain why a soft fork cannot
  do the same, and must give users at least one year between the release and the activation height.
- **Emergency changes.** A change prepared in advance for a known risk may ship in releases before it
  is needed, inactive, as long as its PQIP is Proposed and its activation still requires the miner
  signal above. Example: the ML-DSA emergency soft fork (deployment `mldsaemergency`, bit 1), which
  makes coins spendable only through the SLH-DSA recovery key if ML-DSA is ever broken.
- Signalling shows that miners are ready; it is not a vote. A change that node operators do not want
  will not be followed, whatever miners signal.

## Releases

- Releases are built by the project's build workflow from a public commit, and their `SHA256SUMS`
  file is signed with OpenPGP.
- The goal is **at least 3 signatures by different maintainers**, each with their own key, on every
  release. **Until the project has 3 maintainers, 1 signature is enough.** The keys in use are
  listed in the repository (`contrib/pqch/pqch-releases.asc`) and on the site, with their
  fingerprints.
- A release that changes consensus rules cites its PQIP in the release notes.

## Editors

The editors keep the PQIP repository in order: they check the form, assign numbers, merge accepted
status changes and keep the index. They do not judge the merits of a proposal. The first editors are
the maintainers of `pqch-core/pqch`; anyone with a record of reviews may ask to become one. An editor
who is the author of a PQIP does not merge its status changes.

## Licences of the code

The node (PQCH Core) is MIT, like Bitcoin Core. The applications (the miner, the pool, the light
wallet) are GPL-3.0. A PQIP's reference implementation follows the licence of the program it
changes.

## Security issues

A vulnerability is not reported through a PQIP or any public channel. Report it privately to
community@pqch.org with the subject "security", or through GitHub's private vulnerability reporting
(see `SECURITY.md`). A PQIP that fixes a vulnerability is published after the fix is released.
