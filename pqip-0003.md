# PQIP 3: Merged mining with Monero (AuxPoW) and the Monero key rule

## Abstract

A PQCH block can be proved either by its own RandomX proof of work or by the work of a **Monero block**
that commits to it (auxiliary proof of work, "AuxPoW"). A Monero miner using P2Pool puts a merge
mining tag in its coinbase `tx_extra`; the tag's Merkle tree contains the PQCH block id. If the
Monero proof of work of that block meets the PQCH target, it proves the PQCH block, whether or not
the Monero block is valid on Monero. This PQIP specifies the header flag, the proof format, the
checks that bind the work to one PQCH block, the Monero proof of work, the **Monero key rule** (at
most 4 new RandomX keys in any 4,320 blocks), and, as node policy, how headers with a new key are
handled.

## Motivation

A small new chain has little hash rate, which makes it cheap to attack. Merged mining lets Monero
miners, who already compute RandomX, secure PQCH with the same hashes at no extra energy cost. Both
chains use RandomX, so no new hardware or algorithm is needed; P2Pool already implements merge mining
for auxiliary chains.

## Specification

Constants are those of `src/auxpow.h` and `src/consensus/params.h`. All hashes are 32 bytes in
internal byte order. "Keccak-256" is Monero's `cn_fast_hash` (rate 136, original padding `0x01`).

### Header

- Bit `0x100` of `nVersion` marks a header with an AuxPoW. Such a header is followed, in P2P messages
  and on disk, by a serialized `CAuxPow`. A header without the bit has no `CAuxPow`.
- **The block id stays SHA256d of the 80-byte header.** It does not commit to the `CAuxPow`.
- AuxPoW is allowed from height `nAuxPowHeight` (0 on the main network and the testnet).
- An AuxPoW header obeys every other header rule (target from ASERT, timestamps) and its work counts
  for chain work exactly like a direct header's.

### The proof (`CAuxPow`)

| Field | Content | Limit |
| --- | --- | --- |
| `parent_header` | the Monero block header bytes (major version, minor version, timestamp, previous id, nonce) | 1 to 96 bytes |
| `seed_hash` | the RandomX key of the Monero block | 32 bytes |
| `tx_count` | transactions in the Monero hashing blob, coinbase included (varint) | 1 to 2^20 |
| `coinbase_branch` | the proof of the coinbase (index 0) in Monero's transaction tree | ≤ 21 hashes |
| `coinbase_midstate` | the Keccak-256 state (25 × 64-bit words) after the first `head_size` bytes of the coinbase prefix | — |
| `head_size` | bytes summarised by the midstate (varint) | multiple of 136, ≤ 256 KiB |
| `coinbase_tail` | the rest of the coinbase prefix up to `tx_extra` | < 136 bytes |
| `coinbase_extra` | the coinbase `tx_extra` | ≤ 512 bytes |
| `aux_branch` | the proof of the PQCH block id in the merge mining tree | ≤ 8 hashes (256 chains) |

The largest possible `CAuxPow` is 1,916 bytes, so a `headers` message with 2,000 merged mined headers
fits in one P2P message.

The block body carries, after the transactions, the `head_size` bytes summarised by the midstate
(`CAuxPowCoinbaseHead`). They do not count towards the block weight.

### Header checks

1. The limits in the table hold. If `head_size` is 0 the midstate must be all zeros.
2. `coinbase_extra` is parsed strictly: only the subfields Monero coinbases use (`0x00` padding,
   `0x01` public key, `0x02` nonce, `0x03` merge mining, `0x04` additional public keys), with
   **exactly one** merge mining tag (`0x03`). The tag holds P2Pool's encoding of
   `(n_aux_chains, nonce)`, which must be canonical, and the 32-byte root of the merge mining tree.
3. **PQCH's slot** in that tree is `SHA256(chain_id ‖ nonce as 4 bytes little endian ‖ 'm')`, its
   first 4 bytes read little endian, modulo `n_aux_chains`, where `chain_id` is the PQCH genesis block
   hash (P2Pool's slot rule).
4. The root obtained from the PQCH block id, `aux_branch`, the slot and `n_aux_chains` (Monero's tree
   rules, P2Pool's `get_root_from_proof`, which fixes the proof length from the tree size) must equal
   the tag's root (`bad-auxpow`).
5. The coinbase hash is the Monero transaction id of a version 2 coinbase with RingCT type null,
   computed by resuming Keccak-256 from `coinbase_midstate` over `coinbase_tail` and the `tx_extra`.
   The root of Monero's transaction tree is computed from it, `coinbase_branch`, index 0 and the leaf
   count (`tx_count`, plus 2 leaves for the FCMP++ tree from Monero major version 17), with the same
   proof-length rule.
6. The **hashing blob** is `parent_header ‖ tree root ‖ varint(tx_count)`.

### Proof of work

- Monero major version below 17 (the first varint of `parent_header`): the proof of work hash is
  RandomX v1 of the hashing blob, under the key `seed_hash`.
- Monero major version 17 or later: the hash is the RandomX v2 **commitment**,
  Blake2b-256(hashing blob ‖ RandomX v2 hash of the hashing blob under `seed_hash`), as in Monero and
  P2Pool v5.
- The hash, read as a 256-bit little-endian number, must be ≤ the PQCH target of the header
  (`high-hash`).

### Block checks

- `head` must hash to `coinbase_midstate` (it is `head_size` bytes and leaves Keccak at a block
  boundary), and `head ‖ coinbase_tail` must be **exactly** a canonical Monero version 2 coinbase
  prefix: version 2, unlock time, one `gen` input with the height, the outputs (`txout_to_key`,
  `txout_to_tagged_key`, and from major version 17 `txout_to_carrot_v1`), ending right where `tx_extra`
  starts (`bad-auxpow-coinbase`).
- The block must carry the same `CAuxPow` as its indexed header (`bad-auxpow-mismatch`).
- Both errors mark the block as **mutated**, not invalid: since the id does not commit to the proof, a
  peer sending wrong data must not get a good block marked invalid.

### The Monero key rule

Each block carrying an AuxPoW uses `seed_hash` as a RandomX key. A key is **new** if no block among
the last `nAuxSeedWindow` = **4,320** blocks (about 3 days) introduced it. In any 4,320 consecutive
blocks at most `nAuxNewSeedsPerWindow` = **4** new keys may appear; a header that would be the fifth
is invalid (`auxpow-too-many-seeds`). The rule is checked before any RandomX hash is computed. These
values are provisional and are being calibrated on the testnet.

### Node policy for headers with a new key (informative, not consensus)

This policy is described here because it bounds the cost of the key rule; as node policy it belongs to a separate Network PQIP (the example given in PQIP 1), which will replace this section. Building a RandomX cache for a new key costs about 0.5 s and 256 MiB, and a Monero key is 32 bytes
chosen by whoever sends the header. A node therefore:

- checks a header with a new, uncached key at once when it comes from an outbound peer (one the node
  chose) or a peer with the `noban` permission;
- from an inbound peer, checks **at most one such header a minute** for the whole node, with a cache
  of its own and outside the main validation lock; with fake work the header is refused and the peer
  punished, and no cache in use is pushed out; with real work the cache is kept for the blocks that
  follow; other such headers in the same minute wait, without penalty.

## Rationale

- **Why the id does not commit to the proof.** The same PQCH block can then be proved directly or by
  merged mining, and AuxPoW headers keep the 80-byte header format and the block id of every other
  header. The binding goes the other way: the Monero coinbase commits to the PQCH id.
- **Why the compact proof.** P2Pool coinbases pay hundreds of miners and can be tens of kilobytes.
  The midstate keeps every header small; the block carries the summarised bytes, and the block check
  makes sure they are a real coinbase prefix.
- **Why the canonical coinbase check.** Without it, the split between midstate and tail would be free,
  and one Monero proof of work could hide a second merge mining tag and prove two different PQCH blocks
  (the problem Tari fixed in GHSA-3qmx-q9pv-f3m4).
- **Why only one merge mining tag and a strict `tx_extra`.** Two tags would let one Monero hash point
  at two PQCH blocks; unknown subfields could hide one.
- **Why the key rule.** PQCH nodes do not follow Monero and cannot tell whether a key is Monero's
  real key. Without a limit a miner could choose a new key for every block, making validators build a
  new cache each time, and could pick keys to suit pre-programmed hardware. Monero changes key every
  2,048 blocks (about 2.8 days), so an honest chain introduces 1 or 2 keys per window; 4 leaves room
  for key changes and reorganisations.
- **Why the inbound policy.** Most merged miners run their node at home behind a router, with only
  outbound connections: to the network they are inbound peers. Ignoring new keys from inbound peers
  (the first version of the policy) meant their blocks never reached the network. One check a minute
  bounds an attacker to about 0.5 s of one core and 256 MiB a minute.

## Backwards compatibility

Active from the genesis block on the PQCH networks; no upgrade is needed. A node that does not merge
mine is not affected. Monero is not affected: the tag is an ordinary `tx_extra` field.

## Deployment

Buried: `nAuxPowHeight` = 0. Merged mining is enabled on a node with `-mergemining`, which serves
P2Pool's merge mining API (`merge_mining_get_chain_id`, `merge_mining_get_aux_block`,
`merge_mining_submit_solution`) at `/json_rpc` on the RPC port.

## Security considerations

- The block id not committing to the proof is safe because a wrong or missing proof only marks a
  block as mutated; the good block is accepted when it arrives with its proof.
- Merged mining adds Monero miners' hash rate but also lets a large Monero pool mine PQCH without
  cost. PQCH's reorganisation limit (60 blocks once synced) and payment confirmation guidance apply.
- The key rule bounds the cost of honest validation; the inbound policy bounds the cost of attacks on
  it. Both are being calibrated on the testnet.
