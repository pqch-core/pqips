# PQIP 5: Post-quantum Lightning channels

## Abstract

This PQIP specifies how Lightning payment channels (BOLT 2, 3 and 5) are built on PostQuantum Cash
**without any change to consensus**. Every channel output is a P2MR output (PQIP 2) whose leaves
use hybrid signatures (Schnorr and ML-DSA-44), and every leaf that can hold funds has an SLH-DSA
twin, so that channels survive the ML-DSA emergency soft fork (PQIP 4). Revocation, which in
Bitcoin's Lightning relies on elliptic-curve key tweaking, is done with hash locks on revealed
per-commitment secrets. The PQIP also fixes the time locks for one-minute blocks, the size limits
that post-quantum signatures impose on the peer messages, and one relay policy value that
anchor outputs need.

## Motivation

Lightning gives fast, cheap payments and takes small payments off the chain, which matters even
more on a chain whose signatures are several kilobytes. No Lightning implementation can run on PQCH
today:

- channel outputs are P2WSH or P2TR, which PQCH does not allow (PQIP 2, rule 1);
- revocation keys and per-commitment keys are derived by adding elliptic-curve points. Post-quantum
  signature schemes have no such operation;
- the channel messages assume 64-byte signatures.

Funds in a channel must be as safe against a quantum computer as funds in a wallet.

## Specification

The key words "must", "must not", "should" and "may" are used as in RFC 2119. Everything not
changed here follows BOLT 1–11 as of November 2026.

### 1. Keys

- Each party has, for the channel, one **hybrid signing key** per role: a Schnorr x-only key
  together with an ML-DSA-44 key. The roles are funding, payment, delayed payment and HTLC. Each
  party also has one **SLH-DSA-SHA2-128s key per role**. All keys are derived from the wallet seed
  with the PQCH derivation of PQIP 2's reference wallet, under a channel-specific tag.
- Keys are **not** tweaked per commitment. Post-quantum keys cannot be tweaked, and key reuse is
  safe for these signature schemes. Privacy across commitments comes from P2MR: a script is only
  revealed when its leaf is spent.
- A **hybrid check** in a script is `<xonly> OP_CHECKSIGVERIFY <mldsa> OP_CHECKSIGMLDSAVERIFY`, or
  the non-VERIFY form at the end of a script. An **SLH check** is `<slh> OP_CHECKSIGSLHDSA(VERIFY)`.

### 2. Every output has an emergency twin

For each leaf below that uses hybrid checks, the tree must contain a second leaf with the same
conditions. In that second leaf, every hybrid check is replaced by an SLH check with the same
party's SLH-DSA key for that role. If the ML-DSA emergency soft fork activates, every channel
output can still be spent under exactly the same rules. While ML-DSA is active, implementations
must use the hybrid leaves: they are about four times smaller.

### 3. Funding output

A P2MR output with two leaves:

- A: `hybrid(funding_A) hybrid(funding_B)`, a 2-of-2;
- A′: its SLH twin.

### 4. Commitment transaction

The commitment transaction is a TRUC transaction (version 3). It pays zero fee and has one
**pay-to-anchor output** for fees, as in Bitcoin's zero-fee commitments. Its outputs:

- **to_local** (the broadcaster's own balance), a P2MR output with:
  - leaf L1: `<to_self_delay> OP_CHECKSEQUENCEVERIFY OP_DROP hybrid(delayed_local)`;
  - leaf L2, revocation: `OP_SIZE <32> OP_EQUALVERIFY OP_SHA256 <H(per_commitment_secret_n)> OP_EQUALVERIFY hybrid(revocation_remote)`;
  - and their SLH twins.
- **to_remote**: a P2MR output with `<1> OP_CHECKSEQUENCEVERIFY OP_DROP hybrid(payment_remote)`
  and its SLH twin.
- **offered and received HTLC outputs**: the BOLT 3 conditions, one leaf for each path:
  - success with the preimage (`OP_SIZE <32> OP_EQUALVERIFY OP_SHA256 <payment_hash> OP_EQUAL…`);
  - timeout after `cltv_expiry`;
  - revocation with `H(per_commitment_secret_n)`;
  - and the SLH twins.
  `payment_hash` is SHA-256, as in BOLT 3; second-stage HTLC transactions keep their BOLT 3
  structure.
- **anchor**: one pay-to-anchor output, value 0 (ephemeral dust).

**Revocation.** In BOLT 3 a party revokes an old commitment by revealing a secret that lets the
other party derive the revocation private key. Here the party reveals `per_commitment_secret_n`
itself. The commitment's revocation leaves only open with its SHA-256 preimage *and* the other
party's own hybrid signature, so the secret is useless to anyone else. The secrets come from the
BOLT 3 shachain, so a node stores revocation data in O(log n), as today.

### 5. Signatures in the peer protocol

- `funding_signed`, `commitment_signed` and `closing_signed` carry, for each signature, the
  Schnorr signature (64 bytes) and the ML-DSA signature (2,420 bytes). An SLH-DSA signature for the
  twin leaves is sent only when needed, in a separate message.
- A Lightning message is at most 65,535 bytes. `commitment_signed` carries one HTLC signature
  (2,484 bytes) per HTLC, so **`max_accepted_htlcs` must not exceed 20**. That leaves room for the
  commitment signature and overhead.
- Second-stage HTLC signatures use `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, as with anchors in BOLT 3.
  These hash types are valid for post-quantum signatures (PQIP 2).

### 6. Time locks (one-minute blocks)

The Bitcoin values multiplied by 10, so that the same real time is kept:

| Parameter | PQCH default |
| --- | --- |
| `to_self_delay` | 1,440 blocks (~1 day); maximum accepted 20,160 |
| `cltv_expiry_delta` | 400 to 1,440 blocks |
| `min_final_cltv_expiry_delta` | 180 blocks |

### 7. Node identity, transport and onion (version 1)

- Version 1 keeps secp256k1 for the node id, the Noise transport (BOLT 8), gossip signatures and
  onion routing (Sphinx, BOLT 4). Sphinx relies on blinding elliptic-curve points, and no
  post-quantum replacement is standardised yet.
- **Consequence:** a future quantum computer could impersonate nodes and read recorded routing
  data (privacy). It could **not** move channel funds, which only open with the hybrid and SLH
  checks above.
- Gossip identifies the chain by the PQCH genesis hash. `channel_announcement` proves the funding
  output with the two funding keys' hybrid signatures (about 5 KB).
- A later PQIP should add ML-KEM-768 (FIPS 203) to the Lightning transport (and to the P2P
  transport, BIP 324) and look at post-quantum onion routing.

### 8. Relay policy needed (not consensus)

A fee-bumping child spends the anchor and at least one wallet input. A hybrid wallet input is about
1,064 vB, which is more than Bitcoin Core's TRUC limit for a child (`TRUC_CHILD_MAX_VSIZE`,
1,000 vB). PQCH nodes must relay TRUC children up to **4,000 vB**, enough for three wallet inputs.
Until most nodes do, implementations must fall back to the BOLT 3 anchor format with CPFP on
non-TRUC transactions.

## Rationale

- **No consensus change.** Every construction uses existing PQCH opcodes: the hybrid and SLH
  checks, `OP_SHA256`, `OP_CHECKSEQUENCEVERIFY` and `OP_CHECKLOCKTIMEVERIFY`. Lightning can
  therefore start after the main network launch without a fork.
- **Hash-based revocation.** It is the only revocation mechanism that does not need key tweaking.
  It costs one 32-byte preimage in the penalty witness.
- **SLH twins.** Without them, activating PQIP 4 would freeze every channel output: the
  counterparty may be gone, and the time locks keep running.
- **Hybrid instead of ML-DSA alone.** This is consistent with the wallet and costs 64 bytes per
  signature.
- **Limit of 20 HTLCs.** This keeps the BOLT 1 message size unchanged. Splitting signatures over
  several messages is left for later.

## Backwards compatibility

This is new on PQCH, so nothing existing breaks. Bitcoin Lightning nodes cannot open channels on
PQCH: the chain hash differs.

## Security considerations

- **Fees.** On-chain spends of channel outputs are large: a hybrid 2-of-2 is about 1.9 kvB and an
  SLH 2-of-2 about 4 kvB. A user should only open a channel whose amount justifies the cost of
  closing it.
- **Time locks.** These are scaled for one-minute blocks. Shorter values would give only minutes to
  react to a revoked commitment.
- **Node identity (version 1)** remains vulnerable to a quantum attacker, as section 7 explains.
  Funds are not.
