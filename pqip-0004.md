# PQIP 4: ML-DSA emergency soft fork

## Abstract

This PQIP specifies a soft fork, ready in every node from the genesis block but inactive, that makes
every ML-DSA signature invalid. It is activated by miners through BIP 9 signalling (bit 1, 1,296 of
1,440 blocks) only if ML-DSA is found to be broken. Once active, coins in the standard wallet tree
can only be spent through the SLH-DSA recovery leaf, and the PQCH wallets switch to that leaf on
their own.

## Motivation

The standard P2MR tree (PQIP 2) has two leaves: a hybrid leaf A that needs a Schnorr and an ML-DSA
signature, and a recovery leaf B that needs an SLH-DSA signature. Leaf A is safe while either Schnorr
or ML-DSA holds. If ML-DSA is broken (a flaw in the algorithm or in its implementation) **and** a
quantum computer can break Schnorr, leaf A of every coin is open at the same time, and there would be
no time to write, review and release new consensus code. SLH-DSA relies only on hash functions, the
most conservative assumption available. Having the rule written, tested and shipped in advance turns
the response into a decision by miners and node operators, which can be made in days.

## Specification

### The rule

When the deployment `mldsaemergency` is active for a block, script verification for every input of
that block uses the flag `SCRIPT_VERIFY_MLDSA_DISABLED`. With this flag, `OP_CHECKSIGMLDSA` and
`OP_CHECKSIGMLDSAVERIFY` fail with any **non-empty** signature (`SCRIPT_ERR_MLDSA_DISABLED`), after
the public key size check and before any verification. An empty signature behaves as before
(`OP_CHECKSIGMLDSA` pushes false). Nothing else changes: SLH-DSA, Schnorr, hash locks and time locks
are not affected.

For the mempool, a node applies the flag as soon as the deployment is active for the next block.

### Deployment (BIP 9)

| Parameter | Main network and testnet | Regtest |
| --- | --- | --- |
| Name | `mldsaemergency` | same |
| Bit | 1 | 1 |
| Start time | 0 (from genesis) | 0 |
| Timeout | none (`NO_TIMEOUT`) | none |
| Minimum activation height | 0 | 0 |
| Period | 1,440 blocks (about 1 day) | 144 |
| Threshold | 1,296 (90 %) | 130 (90 %) |

States follow BIP 9: `started` from the first period; `locked_in` after a period in which at least
1,296 blocks signal bit 1; `active` one period later. From the first day of signalling to activation
takes about 2 to 3 days on the main network. Since there is no timeout, the deployment can never
fail; it stays `started` until it locks in.

### Signalling

Nodes **never signal by default** (`signal_by_default = false`). A node sets bit 1 in the blocks it
builds only when started with `-signalmldsaemergency=1`. Nodes of this version do not show the
"unknown rules" warning for blocks that signal bit 1.

### Wallets (informative)

- PQCH Core: when the deployment is active, `send`, `sendtoaddress`, `sendall` and PSBT signing spend
  through the recovery leaf with no configuration, and fees are estimated for the larger SLH-DSA
  witness (about 2,077 vB per input instead of about 1,064 vB).
- Light wallets that cannot query the deployment state may learn it from the node's answer: a
  transaction refused with "ML-DSA signatures are disabled" was not relayed, so the wallet signs the
  same payment again through the recovery leaf, shows it again for confirmation (the fee is higher)
  and uses the recovery leaf from then on.
- Vaults whose recovery leaf has a relative time lock (`<n> OP_CHECKSEQUENCEVERIFY`) can only be
  spent after that delay once the rule is active.

### When to activate (procedure, not consensus; open for discussion)

The project announces a recommendation to signal only if ML-DSA-44 is shown to be broken in a way
that allows forging signatures (a published attack, or a flaw in the implementation used by PQCH
that cannot be fixed quickly by a normal release). The announcement, the reasons and the
signalling instructions are published through the channels listed at pqch.org and signed with the
release key. Activation itself depends only on miners signalling.

## Rationale

- **Why a soft fork.** It only makes invalid what was valid before, so nodes that do not upgrade keep
  following the chain. Since the rule is already in every release, there is nothing to upgrade.
- **Why ready from genesis and not written when needed.** Consensus code written in a hurry is the
  most likely source of a chain split. Shipping it in advance means it has been reviewed and tested
  under ordinary conditions.
- **Why opt-in signalling and no timeout.** The rule must never activate by accident (a default
  setting, a copied configuration), and it must stay available for as long as the chain exists.
- **Why 90 % of one day.** High enough that a minority of miners cannot impose it, short enough that
  the reaction to a break takes days, not weeks.
- **Why only non-empty signatures fail.** An empty signature is the standard way to say "this key does
  not sign" in tapscript; keeping its meaning means scripts that use it as a branch keep their
  behaviour.
- **Why SLH-DSA as the fallback.** It relies only on the security of hash functions, and every
  standard wallet tree already has the SLH-DSA leaf, so no coin needs to be moved before activation.

## Backwards compatibility

Before activation, nothing changes. After activation, transactions that spend through leaf A
(including any signed before activation and not yet confirmed) are invalid and must be signed again
through leaf B. Outputs not created by the standard wallet tree that have no non-ML-DSA spending path
become unspendable; wallets should always include a recovery leaf.

## Reference implementation and tests

- Code: `src/kernel/chainparams.cpp` (`DEPLOYMENT_MLDSA_EMERGENCY`), `src/deploymentinfo.cpp`,
  `src/validation.cpp` (flags for blocks and the mempool), `src/script/interpreter.cpp`
  (`SCRIPT_VERIFY_MLDSA_DISABLED`), `src/init.cpp` (`-signalmldsaemergency`), `src/wallet/spend.cpp`
  and `src/wallet/wallet.cpp` (automatic recovery spending), the Android light wallet
  (`create_tx` with `recovery`).
- Tests: `feature_pqch_mldsa_emergency.py` (signalling only with the option, `locked_in` and `active`
  on regtest, ML-DSA spends refused in blocks and the mempool, SLH-DSA spends accepted, PQCH Core
  wallet and light wallet switching on their own); `pqch_pq_tests` (the script flag).

## Security considerations

- A majority of miners could activate the rule without a real break. The cost to users is higher
  fees (an SLH-DSA spend is about twice the size of a hybrid one), not lost coins, as long as wallets
  use the standard tree.
- SLH-DSA-SHA2-128s signing is slow (seconds on a phone), which is acceptable for an emergency.
- The rule does not protect coins whose leaf A was already spent and whose address was reused; see
  PQIP 2.
