# PQIP 2: Pay-to-Merkle-Root outputs and post-quantum signatures

## Abstract

This PQIP specifies how coins are locked and spent in PostQuantum Cash. Every output that can hold
coins is a **Pay-to-Merkle-Root (P2MR)** output: a witness version 1 program of 32 bytes that is the
Merkle root of a tree of scripts, with no public key and no key path, as in BIP 360. Script leaves
of version `0xc2` ("PQ-script") are tapscript (BIP 342) plus four opcodes that verify **ML-DSA-44**
(FIPS 204) and **SLH-DSA-SHA2-128s** (FIPS 205) signatures. Two rules apply from the genesis block:
outputs of the old, elliptic-curve-only types are invalid, and a script that verifies a Schnorr
signature must also verify a post-quantum signature.

## Motivation

A quantum computer able to run Shor's algorithm at scale would recover the private key of any
elliptic-curve public key it can see. Bitcoin outputs reveal public keys either in the output itself
(P2PK, Taproot key path) or when they are spent, and old coins with exposed keys could be taken. A
new chain can avoid the problem from its first block: no output carries a public key, and every
spending path that uses an elliptic-curve signature also needs a post-quantum one.

P2MR keeps the useful parts of Taproot (a Merkle tree of scripts, only the used leaf revealed,
BIP 341 signature hashes, tapscript) and removes the key path, which is the part that depends only
on an elliptic-curve key.

## Specification

The key words "must", "must not" and "may" are used as in RFC 2119. Constants are those of
`src/script/interpreter.h`, `src/script/script.h` and `src/crypto/pqc/pqc.h`.

### Output rule (rule 1)

From the genesis block, including the coinbase transaction, an output's `scriptPubKey` is valid only
if it is one of:

1. a P2MR output: witness version 1, 32-byte program;
2. pay-to-anchor (witness version 1, program `0x4e73`), used to raise fees (no key, no coins at risk);
3. a witness program of version 2 to 16 (reserved for future soft forks);
4. a script starting with `OP_RETURN`.

Every other output (P2PK, P2PKH, P2SH, witness version 0, bare scripts) makes the transaction invalid
(`bad-txns-output-not-pq`). Witness version 1 with a 32-byte program always means P2MR in PQCH; there
is no Taproot.

### Spending a P2MR output

The witness stack is, from bottom to top: the inputs of the script, the **script**, the **control
block**, and optionally an annex (an element starting with `0x50`, as in BIP 341, non-standard).

1. Without counting the annex, the stack must have at least 2 elements. **There is no key path**: a
   stack with one element fails.
2. The control block is `1 + 32·m` bytes, with `0 ≤ m ≤ 128`. Its first byte `c` must have its lowest
   bit set (`c & 1 == 1`); the leaf version is `c & 0xfe`.
3. The leaf hash is the BIP 341 `TapLeaf` tagged hash of the leaf version and the script. The root is
   obtained by combining it with each 32-byte node of the control block in turn with the BIP 341
   `TapBranch` tagged hash (smaller hash first). The root must equal the 32-byte program. Unlike
   Taproot, the root is not used to tweak any key.
4. By leaf version:
   - `0xc2` (PQ-script): the script is executed as tapscript (BIP 342), with the changes below.
   - `0xc0` (Taproot's tapscript): **invalid** in P2MR (it would allow Schnorr-only spending).
   - any other version: valid without execution, reserved for future soft forks (non-standard).

### PQ-script (leaf version 0xc2)

Tapscript (BIP 342) applies, with these changes:

- **Stack elements and pushes** may be up to **8,192 bytes** (tapscript: 520), so that keys and
  signatures fit.
- **New opcodes**, which in any other context keep their tapscript meaning (`OP_SUCCESS`):

| Opcode | Value | Public key | Signature | Validation weight |
| --- | --- | --- | --- | --- |
| `OP_CHECKSIGMLDSA` | `0xc0` | 1,312 bytes (ML-DSA-44) | 2,420 bytes, plus 1 optional hash type byte | 200 |
| `OP_CHECKSIGMLDSAVERIFY` | `0xc1` | same | same | 200 |
| `OP_CHECKSIGSLHDSA` | `0xc2` | 32 bytes (SLH-DSA-SHA2-128s) | 7,856 bytes, plus 1 optional hash type byte | 800 |
| `OP_CHECKSIGSLHDSAVERIFY` | `0xc3` | same | same | 800 |
| reserved (FN-DSA) | `0xc4`, `0xc5` | — | — | stay `OP_SUCCESS` |

- **Semantics** follow `OP_CHECKSIG` in tapscript. Stack: `<sig> <pubkey>`. The public key must have
  exactly the size in the table, otherwise the script fails (no upgradable key types: new algorithms
  come with new opcodes or leaf versions). An empty signature pushes false (and `…VERIFY` fails). A
  non-empty signature must be valid, otherwise the script fails.
- **Signature size and hash type**: exactly the size in the table, or one byte more; the extra byte
  is the hash type and must not be `0x00` (`SIGHASH_DEFAULT` is written by omitting it). Hash types
  and their meaning are those of BIP 341.
- **Signed message**: the 32-byte BIP 341 signature hash for a tapscript spend (`ext_flag = 1`,
  with the leaf hash and the code separator position), where **`key_version` is 1 for ML-DSA-44 and
  2 for SLH-DSA-SHA2-128s** (0 for Schnorr). A signature hash can therefore never be valid for two
  algorithms.
- **Signature scheme**: the "pure" (not pre-hash) external interfaces of FIPS 204 and FIPS 205, with
  the context string `PQCH/tx/v1` (10 bytes), so that these keys cannot sign for another protocol.
  ML-DSA signatures must be strictly encoded (non-canonical hints are refused).
- **Validation weight**: each input starts with the size of its serialized witness plus 50 units, as
  in tapscript. A non-empty Schnorr signature costs 50, a non-empty ML-DSA signature 200, a non-empty
  SLH-DSA signature 800; the script fails if the budget goes below zero. The costs are proportional to
  measured verification times (Schnorr 40 µs, ML-DSA-44 134 µs, SLH-DSA-128s 565 µs on the same
  machine), so a block costs at most about 0.8 µs of verification per weight unit.

### Hybrid rule (rule 2)

After a PQ-script leaf runs successfully, if it verified at least one non-empty Schnorr signature and
no non-empty post-quantum signature, the spend is invalid (`SCRIPT_ERR_PQ_SIG_REQUIRED`). Scripts
that verify no signature at all (only hash locks and time locks) remain valid.

### Addresses

P2MR outputs are written as segwit version 1 addresses (bech32m, BIP 350) with the human-readable
part `pqc` on the main network, `pqct` on the testnet and `pqcrt` on regtest (`pqc1p…`).

## Rationale

- **Why no key path.** Taproot's key path is spent with only a Schnorr signature, and its output key
  is visible on chain from the moment the output is created. A quantum attacker could spend it. BIP 360
  removes it for the same reason.
- **Why a hybrid leaf and not post-quantum only.** ML-DSA and SLH-DSA are new; a mistake in an
  algorithm or an implementation is more likely than for Schnorr. A leaf that needs both a Schnorr and
  an ML-DSA signature stays safe while either of the two holds. Rule 2 makes sure nobody, by mistake or
  by habit, creates a Schnorr-only leaf.
- **Why ML-DSA-44 and SLH-DSA-SHA2-128s.** ML-DSA-44 has the smallest signatures and keys of the NIST
  lattice standard and verifies fast. SLH-DSA relies only on hash functions, the most conservative
  assumption available; its "s" (small) variant has the smallest signatures, at the cost of slow
  signing, which suits a recovery key used rarely. FN-DSA (FIPS 206) has smaller signatures but was not
  final; its opcodes are reserved.
- **Why the context string and `key_version`.** Domain separation: a signature made for a PQCH
  transaction cannot be replayed as a signature for another protocol, nor for another algorithm in a
  PQCH script.
- **Why 8,192-byte elements.** The largest element is an SLH-DSA signature with its hash type byte
  (7,857 bytes). Raising the limit only inside PQ-script leaves keeps every other script unchanged.
- **Why the validation weight and not a new counter.** The tapscript budget already ties signature
  checks to the size of the witness that pays for them. Setting each algorithm's cost from its measured
  time keeps the worst case per block below that of a Bitcoin block (block weight limit of 2,000,000).
- **Why rule 1 from genesis.** On a new chain it costs nothing, and it means no coin can ever be held
  in an output type that depends only on an elliptic-curve key.

## Backwards compatibility

PQCH is a new chain: these rules apply from its genesis block (buried deployment `pqrules`, height 0
on the main network and the testnet), so no node or wallet needs to upgrade. Bitcoin software cannot
create valid PQCH outputs; Bitcoin addresses are not valid PQCH addresses.

## Security considerations

- **Signature size.** A hybrid spend is about 1,064 vB and a recovery (SLH-DSA) spend about 2,077 vB,
  several times a Bitcoin input. Fees are higher per input; the block weight limit and the validation
  weight bound the cost for nodes.
- **Implementation risk.** mldsa-native is at a published version; slhdsa-c has no published release
  yet and must be fixed at a reviewed commit and audited before the main network starts.
- **Quantum attacks on the Schnorr half.** A spend reveals the Schnorr key of the leaf used. A quantum
  attacker who also breaks ML-DSA could spend coins sent again to that same leaf; wallets must not
  reuse addresses. If ML-DSA is broken, PQIP 4 provides the emergency soft fork that leaves only the
  SLH-DSA recovery leaf.
